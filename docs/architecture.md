# Architecture

This page explains how FSearch for Mac is put together and how a keystroke becomes a result.

FSearch for Mac is a menu-bar launcher (`LSUIElement`, no Dock icon) in front of the `fsearch` Rust daemon. The app draws the UI and talks to the daemon; the daemon owns the index.

## The pieces

1. **The app** (`App/`, SwiftUI and AppKit). It shows the floating panel, Everything-style multi-window search browser (`App/Window/`), menu bar item, onboarding, settings and debug windows, handles `fsearch://` URLs via `AppDelegate`, and exposes the **Search Files** App Intent for Shortcuts.
2. **The daemon**, `fsearch serve`. The app bundles it at `Contents/Helpers/fsearch` and registers it as an `SMAppService` login agent ([`LaunchAgent.plist`](../App/Resources/LaunchAgent.plist), label `com.domfahey.fsearch.daemon`). If a daemon already answers (for example the CLI's login agent), the app uses that one instead.
3. **The socket**, `~/Library/Application Support/FSearch/fsearch.sock`. One JSON object per line in each direction, over a Unix stream socket. Requests are `search` (the default op), `grep`, `status`, `ping` and `save`; every reply carries `ok`, and `{"ok": false, "error": ...}` becomes a `DaemonError` ([`Wire.swift`](../Packages/FSearchKit/Sources/FSearchKit/Wire.swift)).

```text
 +---------------------------------- FSearch.app -----------------------------------+
 |  SearchView -> SearchModel (generation, cancel)          DaemonManager           |
 |                  |                    |                        |                 |
 |        names: DaemonClient   content: DaemonClient   control: DaemonClient       |
 |                  |             LineSocket                      |  (own sockets)  |
 +------------------|--------------------|------------------------|-----------------+
                    v                    v                        v
               ~/Library/Application Support/FSearch/fsearch.sock
                    |  JSON lines: {"id":1,"q":"..."} <-> {"ok":true,...}
                    v
          fsearch serve  (bundled helper, or a CLI daemon already there)
                    |
                    v
          name index + content index on disk
```

The app logs through `os.Logger` (subsystem `com.domfahey.fsearch`, see `App/Support/Log.swift`); see [Collecting logs](reference/troubleshooting.md#collecting-logs).

## FSearchKit and the App target

[`Packages/FSearchKit`](../Packages/FSearchKit) holds everything that can be tested without a UI: the wire types and `DaemonClient.decodeReply`, `LineSocket`, `DaemonClient`, `SearchModel`, `QuerySplit`/`QuerySyntax`, `SearchURL`, `ShortcutSearch`, `SearchWindowQuery`/`SearchWindowRow`/`SearchWindowModel`/`SavedSearch`, `DaemonPlan`, `RestartBudget`, `MenuBarWarning`, onboarding rules, `Recents`, `SearchLog`, `Editors`, `DisplaySafe`, `Launchable`, `DataFolderCheck`, `PeerIdentity`, `SocketHolder`, key handling (`PanelKey`, `PanelState`, `PanelSession`, `HeldKey`, `ExternalOpenGuard` in `PanelKeys.swift`), the panel FSearch menu (`PanelMenuModel`), and row layout (`PanelRows`). It has no dependencies. The `FSearch` target in [`project.yml`](../project.yml) is the glue: windows and the panel (including `AppMenuView` and `PanelFocusCoordinator` for deferred focus handoff with the `⌘/` FSearch menu, plus `SearchWindowManager`, `SearchWindowView`, `SearchPreviewPane`, and `SearchWindowActions` for the Everything-style multi-window search browser — see [ADR 0020](adr/0020-everything-style-search-window.md)), `SMAppService`, Sparkle, the global shortcut, file actions, `AppDelegate` URL-scheme handling (`fsearch://`), and `App/Intents/` (`SearchFilesIntent`). Both targets ship String Catalogs (`App/Resources/Localizable.xcstrings` and `Packages/FSearchKit/Sources/FSearchKit/Resources/Localizable.xcstrings`), synced from compiler `.stringsdata` via `make strings` ([`scripts/sync-strings.sh`](../scripts/sync-strings.sh)). Put new logic in the package and keep the App code thin.

## Entry points beyond the hotkey

- **`fsearch://` URL scheme** ([URL scheme](reference/url-scheme.md)): registered in [`Info.plist`](../App/Resources/Info.plist). [`AppDelegate`](../App/FSearchApp.swift) receives URLs via `application(_:open:)`, parses them with `SearchURL.parse`, buffers cold-launch URLs until `LaunchGuards.startApp` calls `delegate.connect(panel:app:)`, and opens the panel via `PanelController.show(app:search:)` (replacing any 60 s resume state). That external open arms a 0.5 s `ExternalOpenGuard` (on a monotonic `ContinuousClock`) that drops `↵`, `⌘↵`, and `⌘1–9` inside the window so a stray keystroke cannot act on a panel another app just raised.
- **Shortcuts / App Intents** ([Shortcuts](reference/shortcuts.md)): [`SearchFilesIntent`](../App/Intents/SearchFilesIntent.swift) runs in the background (`openAppWhenRun = false`), checks `ShortcutSearch.readsFileContents(query:mode:)` and refuses content, symbol, and inline content-filter (`grep:`, `content:`, `regex:`, `sym:`, `symbol:`) searches unless `allowShortcutsContentSearch` is enabled in Settings (off by default, behind a `Mutex`-guarded `contentSearchAllowed` test seam), then opens its own per-call `DaemonClient` (behind a `Mutex`-guarded `backendFactory` test seam) and queries via `ShortcutSearch.run`. Because it bypasses the panel's `SearchModel`, its queries are not written to the debug search log.

## One keystroke

1. [`SearchView`](../App/Panel/SearchView.swift) changes `model.query`; `.onChange` calls `SearchModel.refresh()`. A mode change calls it directly.
2. `refresh()` handles half-typed filters first: when a half-typed filter extends the previous query in the same mode (`QuerySplit.halfTypedExtends`), `refresh()` returns early without bumping `generation` or cancelling the in-flight task, keeping current rows on screen. Otherwise it bumps a generation counter and cancels the previous in-flight task. Only the newest generation may publish, so a slow old answer is dropped. A blank query, the `?` cheat sheet, a non-extending half-typed filter, a `grep:`/`content:`/`regex:`/`sym:`/`symbol:` with no value yet, or a filter-only content/symbol query sends nothing. Published results are tagged with the query and mode they answer; `resultsAreCurrent` is false until they match the box, so the panel doesn't act on a stale row.
3. `run` picks a backend. Plain name queries go to `names.search(q, limit: 50)`; the request leaves the JSON limit out when the query has its own `limit:`, and the panel shows at most 1000 rows (`SearchModel.shownLimit`). A query with an accented letter also searches its other Unicode normal form, and the hits are merged by path. A query with `grep:`, `content:`, `regex:`, `sym:` or `symbol:` in names mode, and the content and symbol modes, go to `content.grep(...)` with a 250 ms daemon budget. [`AppState`](../App/AppState.swift) creates three `DaemonClient`s (`names`, `content` and `control` for status/ping/save), each with its own `LineSocket`, so a slow content search never queues behind name searches or status checks.
4. `DaemonClient` sends requests one at a time on a serial queue. On connect, `LineSocket` checks with `getpeereid` that the socket belongs to the same user and refuses it otherwise; it retries partial writes and `EINTR`, and rejects a reply line over 64 MiB. Each request carries a fresh integer `id`, and the daemon echoes it in its reply. A call cancelled while queued never touches the socket. `LineSocket` writes the line and reads lines back until `replyIsFor(id, line)` accepts one: a line with a different id is a stale leftover and is dropped, while a line with no id or a null id is accepted so that decoding reports it properly. All of this happens within one timeout (5 s by default); a call that sees only stale lines fails with `.timeout` and closes the connection. If a reused connection was dropped it dials again once and resends; timeouts are not retried.
5. `DaemonClient.decodeReply` turns the line into a `SearchReply` or `GrepReply`, and `SearchModel` publishes `items` and a `SearchPhase` (`idle`, `loading`, `results`, `indexing`, `failed`). A `failed` phase carries a `DaemonError`, and `UserMessage` turns it into the short text the panel shows (see [Troubleshooting](reference/troubleshooting.md)).

## Who owns the daemon

[`DaemonManager.start()`](../App/Daemon/DaemonManager.swift) asks `DaemonPlan.decide` ([`DaemonPlan.swift`](../Packages/FSearchKit/Sources/FSearchKit/DaemonPlan.swift)) with three facts: does something answer a ping, what is the status of our own helper, and is the CLI's agent plist (`~/Library/LaunchAgents/mt.nd.fsearch.plist`) present. The app only checks that the file exists; it never writes there.

- Something answers: use it (`useExisting`).
- Our helper is already enabled: just refresh (`refreshOwn`).
- A CLI agent is installed: ping again for 10 seconds (`cliRecheckWindow`), since its daemon may be restarting. If it still doesn't answer (a leftover plist from a failed install, or a deleted binary), fall back to the bundled helper.
- Our helper is waiting in Login Items: show `needsApproval` and do not register again.
- Otherwise ping again for 3 seconds (`recheckWindow`), then register the bundled helper.

The app never stops, replaces or takes over a daemon it didn't start. It owns the daemon (`ownsDaemon`) only when our helper is `.enabled` and no other process holds the socket. It names the daemon two ways: by the connected peer's code signature (see Security notes below), and by the pid the daemon writes to `<dataDir>/socket.lock`, which any process running as you could write. The peer is named when the control connection last answered, so another daemon may hold the socket since. The more cautious answer wins (`DaemonPlan.holder`): `other` if either says so, so a forged lock or a stale peer can only make the app leave a daemon alone. For that pid it checks with `proc_pidpath` that the process is `Bundle.main`'s `Contents/Helpers/fsearch` (`SocketHolder`). A helper elsewhere (an old one left running after an update) counts only if it sits at a `Contents/Helpers/fsearch` path, or its file is gone, and its signature has our identifier and team. A dev or ad-hoc build, which isn't team-signed, skips the team-signature requirement and accepts an `FSearch.app/Contents/Helpers/fsearch` helper path. It never locks that file. This matters because, since fork commit ba100f4 (in the pinned daemon, not in upstream fsearch; see [ADR 0010](adr/0010-pin-the-daemon-to-a-fork-commit.md)), a CLI agent's daemon makes our helper yield. Our login item is then still enabled, but the daemon answering is the CLI's.

Restart (`DaemonPlan.restartAction`) re-registers only a daemon the app owns: unregister, wait for the old daemon to stop answering, register. It leaves any other daemon that answers running and just refreshes status. When nothing answers and nothing is ours, it runs `start()` again, which rechecks first. One restart runs at a time, and callers arriving meanwhile wait for it. The panel spends at most 3 restarts per outage (`RestartBudget`), refilled when results arrive. Once they are spent, or a search times out, the state says the helper stopped answering, and the menu bar and panel show that instead of "Starting search…". In-app uninstall ([`Uninstaller`](../App/Settings/Uninstaller.swift)) requires positive `.ours` ownership (`DaemonPlan.dataOwnership`) before trashing the data folder and calls `DaemonManager.suspendForRemoval()` (persisting `helperRecoverySuspended`) so automatic recovery stays off until explicit setup.

Our helper is also restarted once in two cases. After an app update, launchd keeps running the old helper binary, so the app compares the bundled helper's identity (build, size and modification time, stored as `helperIdentity`) with the one last seen running. After the menu's "Turn On Full Disk Access…", the daemon fixes its skip list at start, so a running helper keeps working without the new grant. The app polls for the grant every 2 seconds for up to 2 minutes and restarts the helper once as soon as it shows; coming back to the app also restarts it, at the latest.

The plist uses `KeepAlive` with `SuccessfulExit` false. launchd relaunches the daemon after a crash, but not after a clean exit 0, which is how it quits when another daemon already holds the socket.

The bundled helper writes no `daemon.log`. An `SMAppService` agent plist is fixed inside the signed bundle, and launchd doesn't expand `~` in `StandardErrorPath`, so the plist can't name a per-user log file. The helper's stderr goes nowhere, and Index Details says so when the log is empty. The CLI's login agent writes its plist at install time with an absolute path, so its daemon does log. A fix needs the daemon itself to open a log file in its data folder (an upstream ask).

At launch, a second running copy of the app hands over to the first and quits; the first copy raises the panel via `PanelController.showExternally(app:)`, arming the same 0.5 s `ExternalOpenGuard` (monotonic `ContinuousClock`) that drops `↵`, `⌘↵`, and `⌘1–9` inside the window. A copy run from a translocated path or a read-only volume (the DMG) offers to move itself to /Applications and quits, without registering the helper.

## Onboarding, errors and the menu bar

[`OnboardingLauncher`](../App/Onboarding/OnboardingLauncher.swift) shows a four-step window (welcome, helper, Full Disk Access, indexing; `OnboardingStep`) until `onboarded` is set, and starts the helper itself if the window is closed early. Each step checks a fact from the system or daemon (`Onboarding.canContinue`), not a button press. Full Disk Access can be skipped (`skippedFullDiskAccess`).

`DaemonManager.state` is `checking`, `running`, `indexing`, `needsApproval` or `failed`. [`MenuBarStatus`](../App/Errors/MenuBarStatus.swift) maps it, along with `skippedFullDiskAccess` and `dismissedFullDiskAccessReminder`, through `MenuBarWarning.evaluate` to the menu-bar symbol and a message (falling back to the `arrow.down.circle` update indicator when a scheduled update waits and no warning is active). Failure and approval offer "Fix…", which opens Index Details; missing Full Disk Access shows the prominent warning icon and a Full Disk Access action until granted, switching to a quieter dismissible reminder (with "Don't Remind Me") after skipping in onboarding. In the panel, [`DaemonMessageLine`](../App/Errors/DaemonMessageLine.swift) shows daemon query errors and drives the indexing auto-refresh poll, `PhaseMessage` shows phase messages, and [`AppState.searchSettled`](../App/AppState.swift) drives recovery checks and restarts.

## Security notes

The daemon runs with the Full Disk Access you grant it and answers over a local socket in your user account's data folder. The daemon does not verify which program connects to its socket, so other programs that run as the same macOS user may be able to use it. The index is also stored in that folder as ordinary files readable by your account. This matches the trust boundary in [SECURITY.md](../.github/SECURITY.md): a program already running as you can read your files anyway, but the daemon's Full Disk Access reaches folders that program could not otherwise open. Peer verification by the daemon is an open request to the upstream fsearch project; the app does not work around it. In the other direction, the app checks the daemon. It only talks to a socket owned by the same user (`getpeereid`, see step 4 above). It also names the connected daemon by its code signature: on each new connection `LineSocket` reads the peer's audit token (`LOCAL_PEERTOKEN`) and `PeerIdentifier` ([`PeerIdentity.swift`](../Packages/FSearchKit/Sources/FSearchKit/PeerIdentity.swift)) checks the signature of that very process with the Security framework, using the same rules as `SocketHolder`. The token names the process that accepted the connection, so a pid written into `socket.lock` or a reused pid cannot fake it. Only the control connection does this. The result decides ownership (`DaemonPlan.holder` combines it with `socket.lock` and takes the more cautious answer — `other` if either says so) and shows as the **Daemon** row in Index Details. A daemon that is not ours (the CLI's) is still used for searches. It is just never taken for ours, so it is never restarted or removed. Index Details also shows a read-only **Data folder safety** check (`DataFolderCheck`), and in-app uninstall refuses to trash a data folder that is a symlink or owned by another user.

Panel and file actions add several further guards. Before opening a content hit in a chosen editor, [`FileActions`](../App/Actions/FileActions.swift) verifies the resolved app against `Editor.codeRequirement` via two-stage static checking in `CodeSignature.satisfies` (an immediate identity check without hashing resources, followed by an off-main-thread full check including resources, cached by bundle status-change times): team-pinned Apple-anchored certificates for VS Code, Cursor, Zed, Sublime Text, and BBEdit (which also accepts Apple's Mac App Store leaf marker), and Apple-signed (`anchor apple`) for Xcode, falling back to the default app with a footer warning on mismatch. File names and paths are sanitized through `DisplaySafe` (replacing hidden, bidi, and control scalars with `U+FFFD` for display only while actions use the original path), `Launchable` makes `↵` reveal launchable files instead of executing them, `ExternalOpenGuard` drops activation keys (`↵`, `⌘↵`, `⌘1–9`) for 0.5 s after external panel opens (`fsearch://` and second-instance reopen), and Shortcuts content/symbol searches require opting in via `allowShortcutsContentSearch`.

## Debug mode

`debugMode` (menu item or Settings, `DebugMode.set`) adds Index Details and Search Log windows, an orange dot in the panel, and per-search timing. `SearchModel.onSearched` feeds `SearchLog` only while it is on; turning it off deletes the log and closes both windows.

## Test mode

Launch a Debug build with `-FSEARCH_SOCKET <path>` and `LaunchOptions.current.socketPath` (`app.options.socketPath`) uses that socket. Release builds ignore this flag and the XCTest environment variables (`LaunchOptions.testHooksCompiledIn`). In this mode the app never calls `SMAppService` (`service` is nil, `ownsDaemon` is false), never restarts anything, and skips onboarding. Tests supply the daemon themselves with a temporary `HOME` and `FSEARCH_ROOT`, so the real index, login items and `~/Library/Application Support/FSearch` are never touched.

## Tests and benchmarks

- **FSearchKit unit and integration tests**, [`Packages/FSearchKit/Tests/FSearchKitTests`](../Packages/FSearchKit/Tests/FSearchKitTests): `FakeDaemon` is a scripted socket server; `RealDaemon` runs `Vendor/fsearch serve` with a temp `HOME` and `FSEARCH_ROOT` ([`IntegrationTests.swift`](../Packages/FSearchKit/Tests/FSearchKitTests/IntegrationTests.swift)). `RealDaemon` has a watchdog: the daemon runs under a small `sh` wrapper that blocks on a pipe held by the test process, so when the test process exits or crashes, the wrapper stops the daemon and deletes the temp directory. At the start of a run it also sweeps orphaned fixture daemons left by hard-killed runs (see [ADR 0005](adr/0005-tests-never-touch-the-real-index.md)). Run `make test`, or `swift test` in the package.
- **App unit tests**, [`AppTests/`](../AppTests): hosted tests for the app's own logic (DaemonManager, AppState, onboarding, panel input, file actions, menus, URL scheme, App Intents, accessibility, localization, and SwiftUI accessibility-tree view tests via [`AppTests/Support/Accessibility.swift`](../AppTests/Support/Accessibility.swift)). System side effects (SMAppService, NSWorkspace, Trash, Sparkle) sit behind small seams in [`App/Support/`](../App/Support), which the tests replace with fakes; the test host starts nothing (no helper, hotkey, onboarding or updater).
- **End-to-end UI tests**, [`AppUITests/PanelUITests.swift`](../AppUITests/PanelUITests.swift), run by [`scripts/ui-smoke.sh`](../scripts/ui-smoke.sh). The script starts a throwaway daemon in a temporary `HOME` and passes its socket to the test runner via `TEST_RUNNER_FSEARCH_SOCKET`, which launches the app with `-FSEARCH_SOCKET <path>`. Synthesized keystrokes check that FSearch is frontmost (and that the search field has focus for `press`/`type`, or frontmost only for `pressInApp` while Quick Look or menus hold focus). They need a GUI session and don't run in CI.
- **Coverage**: [`scripts/coverage.sh`](../scripts/coverage.sh) runs `FSearchKit`, `AppTests`, and `AppUITests` in its default mode and merges the app `.xcresult` bundles. CI and `make ci` gate both `FSearchKit` (`--kit-only --min 95`) and `AppTests` excluding thin system adapters (`--unit-only --min 95`) at 95% (see [ADR 0012](adr/0012-coverage-gates-at-95.md)).
- **Benchmarks**, `FSearchBench` in the package, run by [`scripts/bench.sh`](../scripts/bench.sh) against a temporary daemon; see [`bench/README.md`](../bench/README.md).
